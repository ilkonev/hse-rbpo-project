# Проектные решения безопасности

### D-01. Серверная авторизация операций с секретами

**Контекст:** аутентифицированный пользователь может изменить идентификаторы секрета и рабочего пространства в запросе или вызвать API напрямую. Без серверной проверки он получает доступ к чужому секрету, выдаёт себе право либо изменяет секрет без разрешения.

**Решение:** перед каждой операцией с секретом, правами доступа или журналом сервер получает текущего пользователя из аутентифицированного контекста, а не из `userId` или роли в запросе. Сервер загружает из PostgreSQL целевой объект, его рабочее пространство и действующие права пользователя. Операция выполняется только после проверки членства в рабочем пространстве и нужного права: просмотра, редактирования, удаления или управления доступом. После отзыва права следующая операция снова читает права из базы данных.

**Обоснование:** сервер остаётся единственным местом, которое принимает решение о полномочиях. Проверка перед каждой операцией не позволяет интерфейсу, переданным идентификаторам и ранее выданному доступу определять право пользователя. Это защищает секреты от чтения и изменения неуполномоченным пользователем и обеспечивает немедленный эффект отзыва доступа.

**Связанные угрозы:** T-01, T-02, T-03, T-05.

**Связанные требования:** SR-02, SR-03, SR-04, SR-05.

**Будущая проверка:**

- **Условие:** существуют два рабочих пространства с разными владельцами, секрет в каждом пространстве и читатель с доступом к одному секрету. Владелец выдаёт читателю доступ к своему секрету, затем отзывает его.
- **Действие:** выполнить прямые запросы к API: от имени читателя подставить идентификатор секрета другого пространства; попытаться изменить секрет без права и выдать себе доступ; после отзыва повторно запросить ранее доступный секрет.
- **Ожидаемый результат:** сервер отклоняет каждый недопустимый запрос, не возвращает значение секрета и не меняет данные. После отзыва доступа повторный запрос читателя также отклоняется.

**Ограничения и последствия:** проверка должна использоваться во всех endpoint'ах, работающих с секретами, правами и журналом. Решение не покрывает запросы без аутентификации, хранение паролей и исключение значений секретов из журнала.

### D-02. Аутентификация перед операциями с секретами

**Контекст:** посетитель без входа может вызвать API напрямую. Если сервер не проверяет аутентификацию до выполнения операции, посторонний получает доступ к секретам или изменяет данные.

**Решение:** сервер применяет проверку аутентификации ко всем endpoint'ам, работающим с рабочими пространствами, секретами, правами доступа и журналом. Исключение составляют только регистрация и вход. При отсутствии или недействительности данных аутентификации сервер завершает запрос до выполнения предметной операции.

**Обоснование:** проверка аутентификации создаёт доверенный контекст пользователя для серверной авторизации и не позволяет неаутентифицированному посетителю обращаться к защищённым операциям API.

**Связанные угрозы:** T-04.

**Связанные требования:** SR-01.

**Будущая проверка:**

- **Условие:** существуют пользователь и секрет в рабочем пространстве; другой посетитель не выполнил вход.
- **Действие:** отправить без данных аутентификации и с недействительными данными аутентификации запросы просмотра, создания, изменения и удаления секрета, а также изменения прав доступа.
- **Ожидаемый результат:** сервер отклоняет каждый запрос до выполнения операции; значение секрета не возвращается, а секреты, права и журнал не изменяются.

**Ограничения и последствия:** каждый новый защищённый endpoint должен быть включён в проверку аутентификации. Решение не защищает от действий пользователя с действующей учётной записью; для этого используется D-01.
